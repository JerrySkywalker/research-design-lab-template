# Method — check a reviewed Lean claim

Use [the package](src/lean/) from a clean checkout. Read the [Blueprint](BLUEPRINT.md), lock and dependency pins as separate review inputs. Establish the reviewed lock revision before accepting changes to proof code.

- Run `lean --version`, `lake --version`, `lake exe cache get Mathlib.Tactic.Ring`, and `python verify.py`. The verifier checks toolchain and manifest pins, anchored evidence fields and records exact source revision hashes. It builds `FormalExample`, enumerates its library declarations and checks transitive axioms and definitional equality of the locked type and cited definition body. Additional theorem hypotheses are part of its type. `propext`, `Classical.choice` and `Quot.sound` are the permitted standard Lean axioms for this reviewed example. Mathematical assumptions such as the domain of a quantifier belong in the reviewed statement.
- Run `lake env lean Drafts/FalseConjecture.lean` to check the counterexample, separately from the accepted import graph. Run `python verify.py --self-test` in a disposable checkout to test rejection of direct and indirect sorry, transitive custom axioms, type and definition changes, draft imports, stale versions and missing provenance.
- Use the existing [run evidence manifest](../../experiments/RUN_EVIDENCE_MANIFEST_TEMPLATE.yaml). [Evidence.yaml](src/lean/review/Evidence.yaml) illustrates inputs in JSON syntax, a subset of YAML. When recording a real run, include the exact source commit or independently resolved hash, retained output reference, hash/size, executed commands and exit codes, per-declaration axioms, lock comparison and review status. A candidate editing both the proof and lock does not establish an accepted revision. Confirm the lock independently in the review diff.
- State the contribution and source provenance. This example is original synthetic scaffolding with AI drafting assistance, uses Mathlib tactics, and asserts neither novelty nor an Owner decision. Source review, evidence admission, interpretation, and adoption are separate.

This sample assumes reviewed code, build configuration and dependencies. Elaboration, build scripts and Lean metaprograms can execute code. For unreviewed or high-risk proof submissions, separately protect a trusted challenge containing the target and its transitive definitions, use a clean sandboxed build with `lake comparator --paranoid` and independent checkers, and retain the challenge and environment results. The local audit cannot establish that higher assurance tier. Keep credentials out of any proof sandbox. See [Lean proof validation](https://lean-lang.org/doc/reference/4.36.0/ValidatingProofs/).

# Maintainer release procedure

This procedure is for the two public template source repositories and their independent ResearchFabric portal. Users of a generated research repository do not need a pair release process or the private coordination repository.

1. **Freeze scope.** Choose the shared pair version and record the exact released `main` and tag targets in both template repositories. Admit only the milestone's frozen work. From v0.6 onward, new research semantics require evidence that they block a stable v1.0 contract.
2. **Implement on branches.** Keep each template's changes reviewable. Do not use actual research repositories as qualification fixtures. Keep generated and heavyweight data out of Git. Update `CHANGELOG.md` for each component.
3. **Validate and qualify.** Run `pwsh -File tests/validate-template.ps1` in this repository and `python scripts/validate_template.py` in the Vault source. Use synthetic instances under a disposable work root for the milestone scenarios. Record commands, outcomes, exact candidate SHAs, and limitations in durable maintainer evidence. Check public safety and fixture fidelity; a validator pass is not a scientific validity claim.
4. **Converge the pair.** At the exact two candidate SHAs, check ownership, terminology, upgrade, governance, storage, and external-reference contracts for contradictions. Keep the two repositories independent; neither CI workflow fetches the other component or private coordination state.
5. **Review PRs.** Open one PR per component, inspect each complete diff, confirm its exact head and base, and require both Windows and Linux template-check CI jobs to pass at the candidate head. If a head changes, requalify it. Stop on unexplained drift or unresolved semantic conflicts.
6. **Merge and tag.** Merge both qualified PRs under repository policy. Compare each merged tree with its qualified candidate tree (for example, `git show -s --format=%T <commit>`). Rerun validators on released `main`. Create and push annotated tags with the same version in both repositories, then verify each remote tag object peels to its released `main`. Stop on a partial merge or tag; do not force a release.
7. **Publish and close.** Record exact PR, candidate, merge, tag, qualification, and limitation facts in maintainer coordination. Update ResearchFabric's stable release set only after both template tags are verified; review its PR and require bilingual docs CI. Recheck public docs, component CI, and clean canonical worktrees before advancing to another milestone.

An instance upgrade is separate: compare prior exact template release, proposed release, and current instance semantically under [the upgrade contract](UPGRADE.md). A template release never authorizes automatic instance mutation.

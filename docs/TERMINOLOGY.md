# Project terminology and Vault references

## Local authority

This Lab owns its project-local terminology. Use the [register](../terminology/REGISTER.md) for navigation and a descriptive note made from the [local term form](../terminology/LOCAL_TERM_TEMPLATE.md) when a definition or context is useful. A term can remain local forever. The Vault, when one exists, owns only reviewed cross-project canonical terminology. This Lab is not a second copy of its glossary.

For a local-only term, record preferred English and Chinese forms, explicit abbreviations and aliases, definition, provenance, and any discouraged wording or publication guidance needed by the project. These are project facts, not cross-project standards.

## Canonical reference

When a reviewed Vault term applies, record its repository URL or stable identity and `terminology/<descriptive-slug>.md` path. Record a full Git commit when an older paper, report, or experiment must reproduce the exact wording used. The repository and path identify the note; the optional commit identifies a historical revision. They are readable Markdown fields, not a universal URI or live link requirement. The Lab remains valid and its validator runs offline when the Vault is unavailable.

Keep only project-specific context and justified deviations in the Lab. Do not copy the whole canonical definition. For current work, review the current Vault note; for historical wording, read it at the recorded commit. A Vault translation change does not silently rewrite this project or its earlier publications.
If the project uses the canonical preferred forms, mark local preferred wording as `use canonical` rather than copying those forms. Record explicit local wording only for a justified project-specific choice.

## Promotion

Nominate a local note for cross-project reuse in its promotion review section. Review overlapping Vault terms, bilingual preferred forms, definition boundaries, and provenance. A reviewed Vault change creates or updates a canonical note, citing the originating Lab repository, note path, and review commit or PR. The Lab retains its original note, project context, and proposal history. A later Lab reference update is a separate deliberate change; no automatic promotion or synchronization occurs. The project may keep justified local wording if the canonical form differs.

Use the [safe upgrade contract](UPGRADE.md) when adopting later template guidance. Populated local terms and the register are instance-owned and cannot be overwritten by a template release.
